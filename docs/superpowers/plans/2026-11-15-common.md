## Global Constraints

Every constraint of `docs/superpowers/plans/2026-11-12-phase-1/00-overview.md`, section "Global Constraints", applies unchanged, with the branch of the table above in place of `phase-1`. In addition:

- **Libraries:** only those the phase's overview lists, each in the task that names it. Anything else is a decision to record with problem, why a few dozen lines cannot do it, license, maintenance state and added size.
- **Outside services** follow overview spec section 5: an interface in `deps`, a real adapter behind environment variables that the agent writes from the linked documentation and **never calls**, a local adapter, a boolean in `GET /api/v1/features`. With `APP_ENV=production`, a `fake` or `console` provider stops the API at start-up.
- **New environment variables** are added to the Zod configuration schema, to `.env.example` with a fake value, and to the README's table, in the task that introduces them.
- **Strings** are final in the spec. A task that says "Strings: spec section N" means: copy every string of that section, character for character, into `apps/web/src/messages/vi.ts` (mail and bot texts into `apps/api/src/mail-templates.ts` and `apps/api/src/bot-messages.ts`). Key names are yours to choose, following the existing key style.
- **Screens without numbers.** Where a task gives no sizes, take them from the nearest existing screen built from the same components; record which screen you copied.
- **Money path.** A task that touches the balance query, a split, or anything that sums money ends with `pnpm db:check-balances` printing `All groups balanced`.
- **Additive API** from phase 5 on: see the phase 5 spec, section 4.1.

## Task 0 of every plan: re-baseline

The specs and plans were written while phase 1 stages 1B–1E were unbuilt. Before any code:

1. Confirm the branch. Run `pnpm check`, `pnpm build`, and every acceptance script of the phases already on `main`, on a reset database. Record the outputs. If something fails on `main`, record it under "Baseline failures" and continue; do not fix other phases' defects unless a task of this plan depends on them.
2. For every file, function, table, route and component this plan names as existing, find it. Write a table in `decisions.md`, "Re-baseline": plan's name → real name and location, or "missing".
3. For each "missing", decide how the affected task changes, and record it. Product behavior in the spec does not change; names and locations follow the code.
4. List which earlier phases are on `main` (`git log main --oneline` and the run directories). Tasks marked "needs phase N" are skipped when phase N is absent, and recorded.
5. Commit the run files: `docs(run): re-baseline <phase>`.

## Per-task procedure and stage gate

Exactly those of the phase 1 overview ("Per-task procedure", "Stage gate"), with these changes:

- The gate replays the acceptance scripts of **every phase on `main`** and of this phase's earlier stages.
- The permission matrix is the phase 1 matrix plus the "Permission matrix additions" of every merged phase's spec and of this one.
- The gate also calls `GET /api/v1/features` with the phase's optional variables unset, and records that every optional capability is `false` and its endpoints answer 404.

Exercises use the four seeded users of phase 0 (Minh, Lan, Hùng, Thu) through the development login unless a task says otherwise. "Fresh group" means a newly created group; role set-up, when a task needs it: Minh owner; Lan joins as editor and claims the member Lan; Hùng joins as viewer and claims Hùng; Thu stays a member with no user.

## Prompt for the implementation agent

Paste the part below the line, with the four placeholders filled from the phase's `00-overview.md`, opened at the repository root on the phase's branch. Reuse it unchanged whenever a session ends before the run is complete.

---

You are the implementation agent for the Sòng Phẳng project. You are doing a phase run: you work through the whole plan without waiting for approval between tasks.

1. Read all of `AGENTS.md` at the repository root, including the "Phase run" section. Every rule applies to you.
2. Read `docs/superpowers/specs/2026-11-15-roadmap-remaining-phases-overview.md` and `<SPEC>`.
3. Read `docs/superpowers/plans/2026-11-15-common.md` and `<PLAN>/00-overview.md`.
4. Confirm you are on the branch `<BRANCH>` (`git branch --show-current`). If not, stop and say so; do not create or switch branches.
5. Open `docs/superpowers/runs/<BRANCH>/progress.md`. Find the first unticked task. Read its stage file completely, then continue from that task. Task 0 is the re-baseline of the common file.
6. For every task follow the per-task procedure, using the `.agents/skills/execute-task/SKILL.md` skill in phase-run mode. After the last task of a stage run the stage gate.
7. Keep going until task `<LAST TASK>` is ticked, then stop.

Rules that are most often broken:

- No automated tests, no test libraries, no committed assertion scripts.
- Do not ask questions and do not wait. Decide, write the decision in `decisions.md`, continue.
- Never weaken a security rule of `AGENTS.md` section 9, never invent a result, never call an outside service, never create an account anywhere. Record what you could not verify under "Not verified".
- One commit per task, only after `pnpm check` passes. Never push. Never touch `main`.
- User-visible strings match the spec character for character.
- Expected numbers in the plan are fixed. If your result differs, the code is wrong.
